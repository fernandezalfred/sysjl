## History

- **Landing Page — Sales & Stock by User** — Replaced the Next.js starter page with a dashboard showing sold/remaining totals per product (Queso, Yogurt) and combined, per-user totals, and a Sale Records view (one row per user/day, merging that day's Queso and Yogurt entries) with a combined total revenue figure. Mobile-first, table-to-card responsive layout. Built against a typed mock dataset behind `getLandingPageData()` for a later one-file Prisma swap. Added Vitest with unit tests for the aggregation logic in `src/lib/landing-data.ts`.
- **Authentication (Login, Sessions, Role-Based Access)** — Set up Prisma 6 + MongoDB (User/Vehicle schema, Role enum) and Auth.js v5 with a Credentials provider: bcrypt password hashing, JWT sessions, role/assigned-vehicle resolved server-side and never trusted from the client. `src/proxy.ts` guards every route except `/login` and `/api/auth/*`. Added a login page/form, sign-out control, and a seed script for one admin and one vehicle user. Password recovery and email confirmation were explicitly deferred. Picked up Prisma's official AI-agent skills as a side effect of `prisma init`. Still open: no in-app UI for an admin to create new users (seed script only) — flagged as a candidate for a future feature.
- **Admin User & Vehicle Management** — Added `/admin/users`: admin-only page to create users, edit name/email/role/password, assign or unassign a vehicle (from existing vehicles — creating vehicle entities is a separate concern per `project-overview.md` §3.1), and deactivate/reactivate accounts (added `User.isActive`; deactivated users are rejected at sign-in). Every Server Action independently re-checks admin role server-side, and `src/proxy.ts` blocks non-admins from `/admin/*`. Fixed two bugs during implementation: a stale vehicle-assignment dropdown after save, and the fix for that breaking the "Saved." confirmation — resolved by splitting the form into a stable outer piece (owns save state) and a remountable inner fields piece (resyncs defaultValue). Known limitation: JWT sessions aren't revoked on deactivation — an already-signed-in user stays logged in until their token expires, though they can't sign in again.
- **Sale Records (Daily Work Records) via Modal** — Vehicle users can now record each working day's Queso/Yogurt quantities taken and remaining through a native `<dialog>` modal at `/records`, and edit their own existing records the same way. Added a `DailyWorkRecord` Prisma model (one row per user per day) and server actions `createDailyWorkRecord`/`updateDailyWorkRecord` (`src/actions/daily-work-records.ts`) that resolve the acting user from the session and enforce per-user ownership — never trusting a client-supplied user id. No delete action; the goals only ever covered create + edit. Also swapped the landing page's `getLandingPageData()` off its mock dataset onto these real records via Prisma, verified live against the real dev MongoDB database (both `/records` and the landing page's Sale Records table render the same seeded record with matching revenue totals). Known limitation: full UI verification was done via curl against the real running app/DB rather than an actual browser click-through, since no browser automation tool was available in this session; the create/edit logic itself is unit-tested the same way every other server action in this codebase is.
- **Sale Records CRUD Moved into Home Page** — Removed the standalone `/records` page and `MyRecordsSection`; create/edit/delete now happen in-place on the landing page's Sale Records section via the same `<dialog>` modal. The modal's inputs flipped from "remaining" to "sold" per product (Queso, Yogurt) — `quesoRemaining`/`yogurtRemaining` stay the stored columns but are now computed server-side as `taken - sold`. Carried the real `DailyWorkRecord` id (`workRecordId`) through the landing page's types so edits target the correct record instead of the aggregated row's synthetic `date|userId` id. Added a user-entered "Total sold" (`totalSold`, `Int @default(0)`) representing the day's grand-total Bs revenue across all 4 products, deliberately **not** cross-checked against Queso sold + Yogurt sold (corrected after initially being implemented as a must-match sum). Added a "Milk & Mote" figure (`milkMoteRevenue = totalSold - quesoRevenue - yogurtRevenue`) on the Sale Records row only — folded into that table's `totalRevenue`, intentionally excluded from `buildProductTotals`/`buildUserTotals`/grand totals elsewhere. Admin creating a record now picks a vehicle user via a required select (server-validated, never trusted from the client for non-admins); admins can edit/delete any record, not just ones they own (admins never own rows themselves). Sale Records now sort by `createdAt` descending (creation recency) instead of the record's own `date`, so a backfilled older-dated record doesn't bump a just-added one off the top. Fixed a Tailwind-preflight bug where `margin: 0` broke native `<dialog>` centering (`dialog:modal { margin: auto; }` in `globals.css`). Found and removed one orphaned pre-existing `DailyWorkRecord` with no known origin, confirmed with the user before deleting. Reused the existing `CreateRecordForm`/`EditRecordForm`/`RecordFormFields` components and `daily-work-records.ts` actions in place rather than rebuilding. Full regression pass: lint, build, and `npm test` (50/50) all green.
- **Daily Winner Highlight (Highest Total Revenue per Day)** — Sale Records and a reworked Totals by User section now mark the day's highest-`totalRevenue` record(s) green with a "Winner (+margin)" badge (`isDailyWinner`/`winnerMargin` on `DailyRecordRow`, computed once in `buildDailyRecords` and shared by both tables); a day needs two or more records before anyone is marked a winner, and ties share the win. `totalRevenue` (sold + unsold/"left" Queso and Yogurt stock value) is the final comparison metric — it was swapped to `totalSold` mid-session after a bug report, then swapped back to `totalRevenue` once the real 2026-10-28 numbers (Raul 2930/3524, Daniel 2825/3254) showed the original totalRevenue-based rule and 270 margin were correct all along. Totals by User was reworked from an all-time per-user aggregate into one row per user per day (Day column, sorted descending, Queso/Yogurt/Milk & Mote in Bs, same two-line sold/left/value display as Sale Records) by deriving its rows from `buildDailyRecords()` instead of aggregating `SaleRecord[]` independently, so both tables always agree on the winner. Also reverted the record create/edit modal's Queso/Yogurt inputs from "sold" back to "left" (`quesoRemaining`/`yogurtRemaining`, stored as entered), and made the date field non-editable — a new record is auto-stamped with the browser's local day (`todayDateString()` in `src/lib/dates.ts`) and an edit always keeps the record's original date, ignoring anything submitted for it. Verified in a real headless-browser session (admin login, Oct 28/27/29 data) against both desktop and mobile layouts; no console errors. Full regression pass: lint, build, and `npm test` (58/58) all green.

The daily winner highlight was widened from just the Total Revenue cell to the **entire row/card** in both Sale Records and Totals by User (desktop `<tr>` and mobile `<li>`), removing the old per-cell `rounded-md bg-green-50` wrapper now that the row/card itself carries the background. Purely presentational — no changes to `isDailyWinner`/`winnerMargin` or any other computed field in `src/lib/landing-data.ts`, so no new tests were needed. - **Admin-Configurable Queso/Yogurt Purchase and Sale Prices** — Added an admin-only `/admin/products` page to set a purchase price and sale price per product (Queso, Yogurt), backed by a new append-only `ProductPrice` Mongo collection (`product`, `purchasePrice`, `salePrice`, `setById`, `createdAt`) — never updated in place, so the full price-change history (who, when, what) is preserved and shown on the page, per `project-overview.md` §4. New Sale Records snapshot the admin's current sale price at creation time (`DailyWorkRecord.quesoSalePrice`/`yogurtSalePrice`, defaulted to the old hardcoded 9/33 so pre-existing documents without the field still read correctly) via `createDailyWorkRecord` → `getCurrentSalePrices()`; `updateDailyWorkRecord` never touches these fields, matching the existing immutable-`date`-on-edit pattern — so a later admin price change never rewrites a past record's revenue. `getLandingPageData` now reads each record's own snapshotted price instead of a global constant, and a real bug was found and fixed along the way: `buildProductTotals` (the summary cards) had been applying *today's* price to *all-time* quantities rather than summing each record's own price — invisible only because the price was a hardcoded constant until this feature. `CURRENT_UNIT_PRICE` survives as the fallback sale price for a product with no admin-set price yet; the seed script seeds one starting price per product idempotently. Verified against the real dev database, not just mocks: changed Queso's price through the live `/admin/products` UI, then queried MongoDB directly confirming every pre-existing record's snapshot stayed unchanged while a newly created record (throwaway test user, deleted afterward with its test price row) picked up the new price. Landed on the same branch/doc as the day-grouping feature above because it was requested mid-session as a distinct, unrelated piece of scope — committed separately (`feat: admin-configurable Queso/Yogurt purchase and sale prices`) per the project's one-feature-per-commit convention. 66/66 tests (8 new/updated), build, lint all green.
