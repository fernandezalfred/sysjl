# Current Feature: Grains & Milk Pages — Group by Day, Quartilla Pricing, Milk Driver Attribution

## Status

In Progress

## Goals

- `/admin/grains`: group purchases by day, matching the Sale Records / Totals by User UI (day header row/card, descending by date), instead of one flat list.
- Relabel the quantity/price fields for grains from "quintal" to "quartilla" — the unit grains are actually priced and purchased in. The three grain items (Maíz Pelado, Maíz con Cáscara, Haba) stay as-is.
- Direct follow-up, same day-grouping treatment for `/admin/milk`, plus one difference: when entering a Milk purchase, the admin now picks a driver (vehicle user) from a dropdown, and that driver — not the entering admin — becomes the purchase's "For" attribution.

## Notes

- The total-cost calculation (`quantity * unitCost`) is already correct for "price per quartilla × quantity of quartillas" — confirmed with the user this is a terminology/label fix, not a formula change. `unitCost`/`quantity` stay the same DB fields and Zod schema; only the i18n labels and the `GrainProduct`/`StockPurchaseRow` doc comments change.
- "stock.quantityQuintal"/"stock.unitCostQuintal"/"stock.quantityUnitQuintal" and the "price per quintal" wording in `grains.subheading` are used exclusively by `GrainPurchasesSection` (confirmed via grep) — safe to rename in place rather than leaving unused keys around.
- Day-grouping needs a raw per-purchase date key. `StockPurchaseRow.createdAtFormatted` is a pre-formatted locale string, not grouping-friendly. Adding `createdAtDate: string` (local YYYY-MM-DD, via a new `formatDateKey()` in `src/lib/dates.ts`) to the shared `StockPurchaseRow` type, populated at both of its construction sites (`admin/grains/page.tsx` and the shared `AdminProductStockPage.tsx` used by Cheese/Yogurt/Milk) even though only Grains groups by it — same precedent as the existing `product` field on that type.
- Scope is the Grains page only; Cheese/Yogurt/Milk (`AdminProductStockPage`/`StockPurchasesSection`) keep their current flat, ungrouped list and "quintal" wording (not part of this request).
- Matching the dashboard's established pattern (`SaleRecordsSection`/`UserTotalsSection`): the day header carries the date, so the per-row/card date is dropped once grouped (not duplicated).
- Direct follow-up: each day's header row/card also shows that day's total cost (sum of `quantity * unitCost` across that day's purchases), e.g. two purchases of 105 and 306.20 same day → header shows Bs 411.20 alongside the date.
- Milk got the same day-grouping + per-day total cost as Grains, plus driver attribution on create. Confirmed with the user: the dropdown picks which vehicle user (driver) the purchase is *for*. `createdById`/`createdBy` keeps meaning the entering admin, for every product including Milk; a new, separate nullable `StockPurchase.forUserId`/`forUser` (Prisma relation name `"StockPurchaseForUser"`, vs. `"StockPurchaseCreatedBy"` on the existing one — both relations needed explicit names once there were two between `StockPurchase` and `User`) carries the driver Milk purchases are for, enforced server-side in `createStockPurchase` (`resolveMilkForUserId`), not just a `required` form attribute, since the client can't be trusted for this. Only active `VEHICLE_USER` accounts are selectable (same list Sale Records already uses). Pushed directly to the live dev Atlas cluster via `prisma db push` (this project's established pattern for schema changes, since MongoDB's connector doesn't support `migrate dev`/`deploy`).
- Since Milk diverges enough now (driver attribution, day-grouping, no current-stock figure), it was pulled out of the shared `AdminProductStockPage`/`StockPurchasesSection` into its own `MilkPurchasesSection`/`CreateMilkPurchaseForm` (mirroring how Grains already has its own section) rather than adding more conditionals to the shared components. `SingleStockProduct` narrowed from `"QUESO" | "YOGURT" | "MILK"` to just `"QUESO" | "YOGURT"`. `EditStockPurchaseForm` (quantity/unit cost only) stays shared across all products unchanged — editing a Milk purchase doesn't reassign its driver, matching the project's existing "edits don't rewrite history" pattern. `MilkPurchasesSection` shows both: "Set by" (admin, reusing the same label/column Grains/Cheese/Yogurt use) and "For" (driver, the new Milk-specific `milk.forDriver` label) as two separate columns/lines everywhere a purchase is listed (desktop table, mobile card), and the edit dialog's title uses the driver's name (`forUserName`) to disambiguate which record is being edited, falling back to the admin's name only for the data-impossible case where `forUserName` is null.
- `createStockPurchase`'s Zod schema gained an optional `forUserId`, read only when `product === "MILK"`; other products ignore it and keep using `session.user.id` exactly as before. 4 new/updated tests in `stock-purchases.test.ts` cover the valid-driver, missing-selection, nonexistent-user, and wrong-role (admin picked instead of a driver) cases.
